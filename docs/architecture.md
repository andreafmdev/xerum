# Architecture — Xerum

## Principle

**JUCE lives at the boundary.** The real-time synth core (`engine/`, `dsp/`) stays free of UI and host glue so wavetable / mod-matrix work can grow without rewriting the plugin adapter.

## Layers

| Layer | Path | Responsibility |
|-------|------|----------------|
| Plugin adapter | `Source/plugin/` | `AudioProcessor`, APVTS, WebView editor |
| State | `Source/state/` | Saved-state format (`StateTree.h`) and the ValueTree → engine snapshot builders (`StateToEngine`). Knows both halves; neither half knows it |
| Parameters | `Source/parameters/` | Single source of parameter IDs + layout, denormalisation, presets. Depends on nothing above `juce_core` |
| Engine | `Source/engine/` | MIDI dispatch, arpeggiator, voice pool, block render, mod matrix snapshot, `ParamCollect.h` (raw APVTS values → `EngineParams`) |
| DSP | `Source/dsp/` | Wavetable oscillator + mipmaps, TPT filter, ADSR envelope, LFO, `WavetableStore` |
| Web UI | `WebUI/` | App shell React + Vite (dev server → WebView): finestra plugin `src/synth/` (900×680, stato, mod matrix, preset) costruita con `@xerum/ui` |
| UI library | `WebUI/packages/ui/` | `@xerum/ui`: componenti synth (Tailwind v4, shadcn base-nova), Storybook, test |
| Bridge | `Source/bridge/` | Web relays, state channel, meters, embedded assets (message thread only) |

```
DAW MIDI ──► PluginProcessor ──► SynthEngine ──► VoiceManager ──► SynthVoice
                    │                                      │
                 APVTS                              dsp:: oscillator/filter/envelope
                    │
             PluginEditor ─── WebView ◄── React (localhost:5173 / fallback HTML)
                                 │
                       bridge::MidiChannel: noteOn/noteOff/allNotesOff ──► MidiKeyboardState ──┐
                                 setWheel(pitch|mod) ──► atomics ──► real MIDI events ──────────┴─► processBlock MIDI
```

## Real-time rules

On the audio thread (`processBlock` → `SynthEngine::process`):

- No heap allocations
- No mutexes / locks
- No file or network I/O
- No logging

Cross-thread assets (wavetables, presets) must use lock-free handoff — double buffer, `AbstractFifo`, or atomic pointer swap (`WavetableStore`, phase 2).

## Plugin window (WebUI/src/synth)

The front panel is `SynthWindow` (`WebUI/src/synth/ui/`): a fixed 900×680 chassis scaled to fit the WebView, laid out as header → wavetable display → Oscillator / Filter / Master plates → tab strip (Envelope, LFO, Mod matrix, Effects, Arpeggiator) → bottom strip (pitch/mod wheels, performance bar, on-screen keyboard — see **Keyboard, wheels and MIDI bridge** below), plus a preset overlay. It is the implementation of the Claude Design template `templates/synth-window/SynthWindow.dc.html` of the Xerum Synth UI project.

- Pure logic lives beside it and is unit-tested: `params.ts` (defaults, labels), `format.ts` (value → text), `mod.ts` (LFO shapes, live modulated values, assignments), `curves.ts` (wave morph, filter/envelope/LFO paths, spectrum), `presets.ts`.
- `useSynth` holds the window state (params, mod matrix, preset, tab, bypass, dirty); `useClock` drives LFO/meter/arp animation. Values are normalised `0..1`.
- **Bridge** (`Source/bridge/`, `WebUI/src/juce/`): every control is a JUCE web relay on an APVTS parameter (`WebRelays`); mod matrix and arp steps live in the APVTS `ValueTree` (`MODS`/`ARP`) behind `StateChannel` (`getState`/`setMods`/`setArpSteps` + `stateChanged`); `MeterChannel` streams `MeterFrame` atomics at 30 Hz as `meters`. The audio thread only loads/stores atomics. `parameters.json` is the single source of truth; `scripts/gen-params.mjs` regenerates `ParameterTable.h` and `params.generated.ts`.
- Without a JUCE host (browser, tests) the UI runs on `FakeBackend` (`?demo` clock on in the browser).
- **Scaling uses `transform: scale()`, and `zoom` was tried and rejected.** `zoom` looks like the better tool — it redoes layout instead of stretching a bitmap — but WebKit, the engine inside the WKWebView the plugin actually runs in, does not implement it the way Chromium does. Measured with Playwright/WebKit at a 1309×873 viewport with `zoom: 1.4544` on the chassis: the chassis' own `getBoundingClientRect()` stayed 900×600 (unscaled) while its descendants were *divided* by the factor rather than multiplied (the wave display, 130 px in layout, measured 89.4 = 130 / 1.4544). In the plugin that showed up as a ~270 px empty band between the panel and the keyboard. Don't reach for `zoom` again without measuring in WebKit first — Chrome will not show the problem.
- **The `<canvas>` in `WaveDisplay` needs the scale handed to it.** `transform` does not touch a canvas backing store, so the wave display stayed at 1× resolution while everything around it grew — it is the largest element in the window, which is most of why the UI read as soft at high scale. The backing store is now multiplied by the applied scale, read back from `getBoundingClientRect().width / clientWidth`. The scale also arrives as a prop, and that part is not redundant: it is the *dependency* that makes the draw effect re-run on resize. Without it the effect ran once at mount, while `sc` was still 1, and the canvas kept that resolution forever (verified: the backing store stayed pinned at 1752 px at every window size).
- Five materials via `variant` (`glass` default, `metal`, `deep`, `soft`, `glow`) — `synth.css` overrides the `@xerum/ui` hardware tokens on the chassis; `glass` and `metal` (from the "Versione glassy" Claude Design project) also restyle the primitives through their `data-slot` / `data-part` (Knob) / `data-key` (Keybed) hooks and the `sx-*` classes the window components carry. In the browser: `?variant=metal&tab=lfo`.
- Brand assets live once in `Resources/branding` (regenerable with `build.mjs`): the header mark and wordmark come from there through the `@branding` Vite alias, the favicon from `index.html`, and the Standalone/bundle icons through `ICON_BIG` / `ICON_SMALL` in `CMakeLists.txt`.
- Every control is an `@xerum/ui` primitive (Knob with modulation rings and drop target, Segmented, Stepper, Meter, Tabs `bar`, Toggle, Panel, Button). Displays specific to the window (filter response, envelope, LFO scope, wavetable stack + spectrum) are app-level canvases/SVGs.
- **Known divergence:** `WaveDisplay` (`WebUI/src/synth/ui/WaveDisplay.tsx`) draws a procedural curve from `WebUI/src/synth/curves.ts`, not the real `.xwt` table data — deliberate, not an oversight.
- **Known gap:** the twelve factory presets (`Source/parameters/presets.json`) have been recalibrated against the current gain staging — each one now states `level`, `drive` and `volume` explicitly, the three that decide whether it clips — but they still have not been auditioned by ear, and the preset browser (`PresetOverlay`) has not been clicked through end to end in the Standalone.

## Motion

Il vocabolario di motion (durate, curve, l'asimmetria d'uscita del vetro) sta in un solo posto, `WebUI/packages/ui/src/motion.ts`; `theme.css` lo rispecchia come custom property (`--dur-*`, `--ease-*`) e `motion.test.ts` tiene le due copie insieme, verificando che non divergano.

- **Varianti** — ogni materiale del chassis può scostarsi dal vocabolario di base: `glass` rallenta `--dur-state` a 140ms e sostituisce `--ease-snap` con `--ease-glass`; `metal` stringe sia `--dur-layer` (160ms) che `--dur-state` (100ms). Le regole vivono in `WebUI/src/synth/ui/synth.css`, sugli attributi `[data-variant="…"]` del chassis.
- **Enforcement** — `scripts/check-motion.mjs` applica whitelist delle proprietà animabili, divieto di layout animations e durate solo da token, ed è il primo passo di `pnpm build` (`check:motion && ui:build && tsc --noEmit && vite build`): la build fallisce prima ancora di compilare. Le deroghe sono per path completo dalla radice del repo, non per basename — due file omonimi in cartelle diverse condividevano in silenzio la stessa deroga, prima di questo cambio. Le poche righe dove un valore letterale è legittimo (l'aurora dell'ambient in `glass`, per esempio) sono escluse con blocchi marcatore `<nome>:start`/`<nome>:end`, visibili, cercabili e motivati da un commento accanto — mai un'indirezione silenziosa.
- **Quello che lo script non vede** — `check:motion` non legge i valori dentro un `@keyframes`, non distingue un `box-shadow` animato su una piccola superficie da uno su una grande, e non raggiunge un'animazione creata in JavaScript (WAAPI incluso). Un build verde dice che le regole meccaniche sono rispettate, non che l'animazione è buona: il resto resta responsabilità della review.
- **`@xerum/ui` è una libreria compilata** — l'app risolve il pacchetto sul suo bundle costruito (`dist/index.js`), non sui sorgenti in `packages/ui/src`. `pnpm build` ricompila prima la libreria (`ui:build`) e poi l'app: una modifica dentro la libreria resta invisibile nell'app in esecuzione finché quel passo non gira di nuovo. È costata tempo vero durante questo lavoro.
- **Reduced motion ha due metà** — una regola CSS globale (`@media (prefers-reduced-motion: reduce)`, in `index.css` e ripetuta in `synth.css`) copre tutto ciò che è CSS puro; `MotionConfig reducedMotion="user"`, alla radice di `App.tsx`, copre gli `m.*` di `motion/react`, che quella media query non tocca. Il colpo di luce del cambio preset (`SynthWindow.tsx`) è un'animazione WAAPI e non è coperta da nessuna delle due: legge `matchMedia("(prefers-reduced-motion: reduce)")` da sé, ad ogni cambio di preset, non una volta sola all'avvio.
- **L'ambient senza re-render** — `useMeterConductor` (`WebUI/src/synth/ui/conductor.ts`) è un solo `requestAnimationFrame` coalescente per l'intera finestra: si iscrive a `meterStore` e scrive tre custom property (`--m-out`, `--m-env`, `--m-lfo`) direttamente sul chassis via `style.setProperty`, senza passare da stato React. È la forma scelta apposta: far ri-renderizzare N componenti trenta volte al secondo dentro una WebView che divide la CPU col motore audio è esattamente il costo che questo loop evita.

Il progetto di riferimento è `docs/superpowers/specs/2026-09-20-motion-system-design.md`.

## Keyboard, wheels and MIDI bridge

There is no native component next to the WebView any more — the editor is a bare `WebBrowserComponent` that fills the whole window. The keys, the pitch/mod wheels and the octave/velocity controls all moved inside the chassis, as its bottom strip: `BottomStrip` (`WebUI/src/synth/ui/BottomStrip.tsx`) lays the two `@xerum/ui` `Wheel`s (`PB`, `MW`) beside a column holding `PerformanceBar` — octave shift, velocity, a MIDI-activity dot, the two meters — over `Keybed` (`WebUI/packages/ui/src/components/Keybed/`), the four-octave key strip itself. None of it is JUCE chrome any more; it is `@xerum/ui`, same as every other control in the window, and it goes through design-sync like the rest.

**Bridge** — `bridge::MidiChannel` (`Source/bridge/MidiChannel.{h,cpp}`) is what the strip plays through: four native functions, `noteOn(note, velocity)`, `noteOff(note)`, `allNotesOff()`, `setWheel(kind, value)`. Notes land in the processor's `MidiKeyboardState` (`PluginProcessor::getKeyboardState()`), the very same one `processBlock` already merges into the host MIDI buffer — a note played from the UI is indistinguishable from one played on a DAW track, and nothing downstream needs to know the difference. Wheels can't travel that way — `MidiKeyboardState` only carries notes — so `setWheel` instead writes into two atomics on the processor (`uiPitchBend_`, `uiModWheel_`, `-1` meaning "untouched"), which `processBlock` turns into real MIDI pitch-bend / CC1 messages prepended to the block; from there down, the arpeggiator, the engine and the mod matrix have no way of telling a drawn wheel from a physical one. Those atomics outlive the editor, so the drawn `MW` has to be told where the engine already is: `BottomStrip` seeds its mod position from `mw` in the **first** `meters` frame after mount and then unsubscribes — once, not continuously, which would fight a drag in progress — and it pushes nothing on mount, which would stomp a CC 1 that came from real hardware. `PB` needs none of this: `springBack` puts it at centre anyway. There is no event back to the UI to say a note is sounding — the strip reads that off the note mask carried in the `meters` frame instead (below), the same 30 Hz channel that already carries meter and mod levels.

**Computer keyboard** — `BottomStrip` also plays from QWERTY, which is what the deleted native strip did with `setKeyPressBaseOctave (5)`. Window-level `keydown`/`keyup` listeners map the two standard rows onto semitones above the strip's current lowest C — `A W S E D F T G Y H U J` for one octave, `K O L P ;` continuing above — and feed the very same note-on/note-off path as the pointer, at the performance bar's velocity. It reads `event.code`, not `event.key`, so the rows stay under the same fingers on a non-QWERTY layout. System auto-repeat is ignored, a keydown while a text field has focus is ignored, `keyup` releases the note the `keydown` actually started (so shifting the octave mid-press cannot hang one), and window `blur` panics and forgets everything held — without a `keyup` the map would otherwise believe that key were still down. The caveat is the one the spec already recorded: it only works while the WebView has keyboard focus, and hosts that swallow key events from web views (FL Studio 25 as of Sept 2026) will swallow these too.

**Note mask** — `engine::SynthEngine::getActiveNotesLo()`/`getActiveNotesHi()` publish one bit per MIDI note (0..63 in `notesLo`, 64..127 in `notesHi`) into `engine::MeterFrame`. The audio thread writes them, and the reader takes them as an instantaneous state rather than a peak — like `lfo`/`mw`, loaded rather than exchanged to zero — because a held note is a state, not a transient. `bridge::MeterChannel` can't hand a `uint64` to JSON as-is (a double's mantissa doesn't hold 64 bits exactly), so each word is split into two 32-bit properties on the `meters` event — `n0`/`n1` from `notesLo`, `n2`/`n3` from `notesHi` — alongside `in`/`out`/`lfo`/`env`/`env2`/`vel`/`mw`/`arpStep`. `WebUI/src/juce/backend.ts` reassembles them (`noteMaskOf`) into four 32-bit words, and `Keybed` checks `isNoteActive` against them to light a key without going through React state — the mask is applied by mutating `data-active` through a ref at 30 Hz, the same reason `BottomStrip` reads the frame directly instead of through `useMeterValue`. Every other consumer goes through `useMeterValue(selector)` (`WebUI/src/juce/hooks.ts`): one listener per backend in `WebUI/src/juce/meters.ts` holds the frame (with the peak hold on `in`/`out`), and a component re-renders only when its selected value changes — the arp playhead of a step when that step turns on or off, not thirty times a second.

**Sustain pedal** — CC 64, and which layer owns it depends on the arpeggiator. With the arp **off**, `SynthEngine::handleMidiEvent` arms `VoiceManager::setSustainPedal`, and a note-off is not translated into something else — it is **deferred**: `held_` keeps the key exactly as it was, the voice is untouched, and the only trace is a bit in `sustained_`. Lifting the pedal replays those note-offs through the ordinary `noteOff()`, oldest key first. The order is load-bearing rather than cosmetic: in Mono every note-off that touches the sounding note walks the voice back to the previous key and retriggers the envelope, so releasing newest-first would give three retriggers — an audible blip — where a three-note chord held by the pedal should give none. With the arp **on**, the pedal is a **latch** instead: `Arpeggiator` marks released keys `latched` rather than dropping them, so the sequence keeps running on the chord with every finger off the keys, and `heldCount_ > 0` does the rest without any other branch knowing about the pedal. The arbitration is one condition in the CC 64 branch (`isSustainPedalOn() && ! params_.arp.on`) plus one line per block that disarms the pedal when the arp turns on; it has to exist because the arp rewrites the MIDI buffer *upstream* of the voices, so a sustain armed underneath would hold every note the arp emits and pile the sequence into a cluster that grows each step instead of arpeggiating. The CC 64 is forwarded downstream either way. The note mask follows what is audible: a key held by the pedal stays lit on the `Keybed` and goes dark when the foot comes up, which `SynthEngine` tracks in its own `sustainedNotes*` words — a separate mask from `VoiceManager`'s, because one decides when a voice releases and the other when a key on the UI goes out. No parameter in `parameters.json`: the pedal is MIDI, not preset state.

**Pitch bend** — `pbRange` (`parameters.json`) sets `EngineParams::pitchBendRangeSemitones`; the `PB` wheel's live position (0..1, 0.5 = center) becomes a real pitch-bend MIDI message as described above, and `SynthEngine::pitchBend_` bends every sounding voice — arpeggiated notes included — by up to that many semitones at full deflection, springing back to the centre on release (`Wheel`'s own `springBack`, set on the `PB` wheel in `BottomStrip.tsx`, not anything the bridge does).

**Layout** — the strip is inside the chassis now, not a `PluginEditor` layout concern. The window's *width* is still the only free variable the editor derives everything from (`PluginEditor.cpp`): scale = `width / 900`, clamped to `0.72 … 1.5` (same ceiling as the web fit), and the WebView — the whole editor — is `ceil(H × scale)` tall, enforced by `ChassisConstrainer`. `H` is `680` — the 670 px its `shrink-0` children actually occupy (20 padding + 40 header + 130 wave display + 224 panels + 124 tab area + 108 bottom strip + four 6 px gaps) plus 10 px of breathing room at the bottom, the same 10 the pre-strip 600 box had. It is exported from `WebUI/src/synth/ui/SynthWindow.tsx` as the one source of truth; `.sx-chassis` in `synth.css` and `kChassisHeight` in `PluginEditor.cpp` both carry a comment pointing back at it, and a web test (`SynthWindow.test.tsx`) pins the CSS copy against it. The editor still loads the UI with `?gutter=0`, which tells `SynthWindow` to fit the chassis with no side margin (default `16`) and mark it `data-attached`. That attribute used to square the chassis's bottom corners, back when the native keyboard strip needed to butt flush against them from underneath; now that the strip lives inside the chassis, that CSS rule is gone and the corners stay rounded in every state. `data-attached` therefore has **no CSS consumer at all** today — it does not drop the margin either, `gutter` does that itself inside the fit computation. It is kept only as a host-detection hook ("this chassis is filling a WebView") for anything that later wants to read it, and a test pins it so it is not lost by accident. Changing either side of the geometry contract (`H`, the `gutter` default, the fit formula) desyncs `SynthWindow.tsx` and `PluginEditor.cpp`: keep the three copies of `H` in step.

**MIDI inputs** — `bridge::MidiDeviceChannel` (`Source/bridge/MidiDeviceChannel.{h,cpp}`) answers `getMidiInputs()` with `{ host, devices: [{ id, name, enabled }] }` and applies `setMidiInputEnabled(id, enabled)`, and emits `midiInputsChanged` when the `AudioDeviceManager` changes. It only has a device manager in the Standalone (`StandalonePluginHolder::getInstance()`, under `JucePlugin_Build_Standalone`; the holder's `currentInstance` is `inline static`, so the include is harmless in the other formats), where JUCE already persists the choice in its settings; in VST3/AU it answers `host: true` with an empty list and the bar keeps the "MIDI HOST" label. The bar's `MidiSource` shows a `Select`: "Tutti gli ingressi" enables every device, a device enables that one and disables the rest; it displays the device when it is the only one enabled, otherwise "Tutti gli ingressi". The payload is built by `bridge::midiInputsToVar` (header-only, tested without a WebView).

## Phase 1 behaviour

- Instrument plugin: AU + VST3 + Standalone
- MIDI note on/off allocates voices (16 simultaneous, a 19-slot pool, quietest-releasing steal with a fade)
- The sustain pedal (CC 64) holds notes with the arp off and latches the held chord with the arp on — see **Keyboard, wheels and MIDI bridge** above
- The engine is audible: a wavetable oscillator with band-limited mipmaps (`dsp::WavetableOscillator` / `dsp::MipTable`) feeds an exponential ADSR (`dsp::ADSREnvelope`) into a TPT state-variable filter (`dsp::StateVariableFilter`, 1 or 2 stages), then the chorus and the plate reverb. 54 of the 56 parameters in `parameters.json` are wired end to end — all of them but the two listed as inert below:
  - **Osc** — `oscOn`, `wtIndex`, `unison`, `oct`, `semi`, `wtpos`, `detune`, `fine`, `pbRange`, `level`
  - **Filter** — `filtOn`, `ftype`, `slope`, `cutoff`, `res`, `drive`, `keytrk`
  - **Master** — `voiceMode`, `pan`, `glide`, `volume`, `bypass`
  - **Env** — `att`, `dec`, `sus`, `rel`, `envVel`, and the second envelope's `att2`, `dec2`, `sus2`, `rel2`
  - **LFO** — `lshape`, `lsync`, `lretrig`, `lrate`, `lphase`, `lfade`
  - **Chorus** — `fx1On`, `chRate`, `chDepth`, `chMix`, `chFeedback`; **Reverb** — `fx2On`, `rvSize`, `rvDamp`, `rvMix`, `rvPredelay`, `rvDecay`
  - **Arp** — `arpOn`, `arpMode`, `arpRate`, `arpGate`, `arpOct`, `arpSwing`

  `pbRange` is the only one of the 54 with no control in the window: it is how many semitones the `PB` wheel bends at full deflection, default 2 — see **Keyboard, wheels and MIDI bridge** above
- The mod matrix is live: five sources (`lfo`, `env`, `env2`, `vel`, `mw`) onto eight targets (`cutoff`, `res`, `wtpos`, `level`, `pan`, `fine`, `drive`, `warp`), at control rate — see **Modulation** below
- `warp` is oscillator **sync** (`dsp::WavetableOscillator::setWarp`): the phase read from the frame runs `1 + 3·warp` times per period, the mip level follows the effective frequency `f·(1 + 3·warp)`, and `WaveDisplay` draws the same mapping. Default 0 = the exact identity. It is the eighth mod target. `envCurve` shapes the three segments of the amplitude envelope (`dsp::ADSREnvelope::setCurve`): 0 is the one-pole exponential, +1 a straight line in the nominal time (overshot target, clamped level), −1 an earlier knee with the same duration. ENV2 keeps curve 0.

## Parameter mapping

`Source/engine/ParamCollect.h` holds `collectEngineParams`, a header-only template that turns raw 0..1 parameter values into an `engine::EngineParams`. It takes an accessor keyed by `params::ParamSlot` (an enum, not a parameter id string) instead of reading the APVTS directly, for two reasons: the conversion arithmetic can be exercised in `XerumTests` with a fake accessor, no `juce_audio_processors` link needed; and at runtime `PluginProcessor` resolves one array of raw parameter pointers once in its constructor (`paramSlots_`, indexed by `ParamSlot`), so the per-block cost is a single array read per parameter — no name lookup, no string comparison.

This split exists because of a bug: an early version cast a denormalised `oct`/`semi` value with `(int)` instead of `juce::roundToInt`, truncating toward zero and landing on the wrong note for several settings (`denormalise()` can return a hair under the true integer, e.g. `7.999998`). The regression test written against that bug reimplemented the `Map::Linear` formula by hand, because at the time the real conversion lived inside `PluginProcessor.cpp`, which pulls in `juce_audio_processors` — a library `XerumTests` doesn't link — so the test verified its own copy of the arithmetic, not the code that ships. `ParamCollect.h` was carved out precisely so a test could call the real `collectEngineParams` (`Tests/ParamCollectTests.cpp`): if the truncating cast came back, that test would catch it; the earlier, hand-rolled one would not. Don't collapse this back into `PluginProcessor` for the sake of one fewer header.

**`getRawParameterValue` returns natural units, not normalised ones — and that is not the same thing for every `Kind`.** `Kind::Float` parameters are created with `NormalisableRange {0, 1}` (`ParameterMapping.h`), so for them natural and normalised coincide and `denormalise()` is the right conversion. `Kind::Choice` arrives as the option index, and `Kind::Bool` as 0 or 1; both are consumed as such. `Kind::Int` — `oct`, `semi` and `pbRange` — is created as a `juce::AudioParameterInt` over its own range, so the accessor hands over −3..3, −12..12 and 0..24 directly. They must be rounded, never denormalised.

Denormalising them was a real bug that shipped for months. At the factory default of 0 and 0 it produced −3 octaves and −12 semitones, so **every note sounded four octaves below the key played** — a middle C came out at 16 Hz, below the fundamental being audible at all, which reads as a dirty, broken tone rather than as a transposition. Worse, `denormalise()` clamps its input to 0..1, so the octave knob could only ever produce the two extremes of its range: natural ≤ 0 gave −3, natural ≥ 1 gave +3, and no position gave 0.

Every test in the suite missed it because they all exercise `collectEngineParams` through a fake accessor that hands over normalised values — which is precisely the assumption under test. The seam between the real APVTS and the engine had no coverage at all, since `XerumTests` did not link `juce_audio_processors`. It does now, and `Tests/ParameterSeamTests.cpp` builds the real parameter layout, reads the real raw pointers, and pins the conversion for all four `Kind`s. **When adding a parameter kind, add a case there**: a fake accessor cannot tell you what JUCE actually puts in that atomic.

## Voice engine

**Headroom.** `Source/engine/SynthVoice.cpp` applies a fixed per-voice gain, `kVoiceHeadroomGain = 0.63f` (-4 dB), to every sample before panning — not a `1 / numVoices` divisor, which would pump the overall level up and down every time a note starts or ends.

That constant is not a round number picked for comfort: **the four-note chord sets it, and now the worst case sets it too.** Both are measured by the gain-reduction method described below, at the soft clipper's input. At `level = 1.0` and the default `volume`, four notes present **0.797** against the clipper's 0.95 threshold — **1.5 dB of margin**, which is a stated design quantity and not an accident. The rule is that it never goes below 1 dB, and the arithmetic behind that rule is 1:1: every decibel of chord margin is a decibel of instrument level, because everything upstream of the clipper is linear in this constant.

The reference level everybody quotes for this kind of instrument — around -14 dBFS RMS on a single note, where Serum and Vital sit — is *not reachable here*, and the reason is arithmetic rather than caution. The crest factor between a single note's RMS and a four-note chord's peak is fixed at 16.4 dB. Put the note at -14 dBFS RMS and the chord lands at +0.5 dBFS even after the default `volume` of 0.8 — above full scale, so **no threshold and no soft-clipper shape with a ceiling at 1.0 can pass that chord intact**. The two targets do not coexist; the clean chord wins.

**The single note's level is not one number, and that is worth knowing before quoting one.** Measured at the plugin output with `level = 1.0` and `volume = 1.0`, no effects, filter at Butterworth Q, the same note spans **-14.0 to -17.1 dBFS RMS** across the six factory wavetables — *Basic Shapes* (the default, `wtIndex` 0) at -14.0, *Vocal Formant* at -17.1. On the factory patch, whose filter sits at 1.45 kHz, the same six span -15.6 to -20.2. The figure this document used to quote, -15.4 dBFS, was *Analog Saws* on the test patch; it is now -16.4. The instrument's own material is spread wider than the retune moved it, so "single note at -14 dBFS" describes a patch, not an instrument.

**Before and after**, all at the soft clipper's input unless marked, all by the gain-reduction method, all on the current chain:

| | -3 dB (`0.71`) | -4 dB (`0.63`) |
|---|---|---|

Three of those rows were failures before this retune, not just tight numbers: the four-note chord had a margin indistinguishable from zero (the constant had been chosen on the point where the chord grazed the threshold, so the margin *was* the rounding), the worst case sat **a decibel above** the +8 dBFS ceiling the instrument gives itself, and *Acid Line* engaged the clipper on an ordinary chord while this document claimed it reached 0.84. The price of fixing all three is the first three rows: **one decibel of instrument level**, on a target that was already 1.4 dB out of reach.

Not all of the drop in the matrix rows is the constant. The `drive` map went quadratic in the same pass (see below), and since the stress test steps `drive` between the ends of its travel, the modulated values in between now land on fewer decibels: that alone took the full-matrix unison 8 case from 2.83 to 2.66 before `kVoiceHeadroomGain` moved at all. The rest, and all of the chord and preset rows, is the constant.

**How the clipper's input is measured, and how it used to be measured wrongly.** Lower the master gain until the clipper stays off, *verify* it stayed off, measure the peak, and rescale. Everything upstream of the clipper — the voices, the effects stage — is exactly linear in the master gain, so the rescaling is exact and not an estimate. The method this document used before, inverting `softClip` analytically on the output peak, is exact in exact arithmetic and **ill-conditioned near saturation**: an output of 0.9983 maps back to 2.36 and 0.9990 to 3.40, so seven ten-thousandths of output become 3.4 dB of estimated input. That is where the old `3.48 (+10.8 dBFS)` full-matrix figure came from; the true number for that same configuration was 2.36. `Tests/ChorusTests.cpp` was the last place still using the inversion and has been ported. Two smaller traps live in the same family: the probe must render one silent block *before* the note, because `applyGainRamp` starts from `previousMasterGain_`, which is still 1.0 on the very first block — without it the peak you measure is the gain ramp, up to eight times the signal; and the window matters, because sixteen notes struck on one sample sum in phase for the first millisecond and present 5.2 dB more than the same sixteen notes sustained.

**What the effects stage costs, measured on the current chain.** Both effects default to on, and at factory settings they *return* headroom rather than take it: the dry branch of the `sin3dB` mix at 30 % is 0.891, and the wet branch — the same signal delayed and spread — does not rebuild that peak. On the full-matrix stress pass (`Tests/ModulationStressTests.cpp`, "matrix pieno e stadio FX acceso"): chorus at factory **-0.17 dB**, reverb at factory **-0.70 dB**, chorus at 100 % mix and feedback **+3.01 dB**, both effects at full travel **-4.09 dB** — a reverb at 100 % wet *replaces* the resonant peaks with a diffuse tail, which is why the worst case is not the sum of the two. On a six-note chord through a Q 2 filter: chorus at factory **-0.68 dB** (`Tests/ChorusTests.cpp`), reverb at factory **+0.25 dB**, at 100 % wet **+2.31 dB** peak and +2.23 dB RMS, everything at full travel **+3.08 dB** (`Tests/ReverbTests.cpp`).

**Three effects, in the order the patch chooses.** The stage is a rack of three fixed slots — chorus, delay, reverb — and `fxOrder` picks one of three permutations (`cdr` is today's chorus → reverb with the delay in between, `dcr` puts the delay first, `crd` puts it last). `SynthEngine::processFxChunk` calls one method per effect in that order; the chorus and reverb methods are the previous code moved line for line, so with the delay idle the orders that keep chorus before reverb execute the old operations in the old sequence, and `Tests/FxRackTests.cpp` pins `cdr` and `crd` as bit-identical. The delay (`dsp::StereoDelay`) is two Lagrange-3 lines of two seconds with feedback up to 90 % through a one-pole low-pass (20 kHz → 500 Hz, log), optional ping-pong (mono-summed input into the left line, each line feeding the other) and a 50 ms half-life on the time, so a change glides the echoes' pitch instead of clicking; synced, its time is `1 / dsp::syncedRateHz` — the LFO's division table, one table for both — clamped to the line. Its slot follows the reverb's shape (gain crossfade, `DryWetMixer`, shared dry copy) without the chorus's priming or the reverb's input ramp: an empty line fed a continuous input grows its echoes from zero by construction. The ringout is the longest tail among the running effects (`StereoDelay::tailSeconds(time, feedback)` for the delay, capped at 60 s), and `getTailLengthSeconds` adds that same figure to `kDeclaredTailSeconds` only while the delay is on. The eight parameters sit at the end of `parameters.json`, the delay defaults to off, and no factory preset turns it on: every existing project loads and sounds as before. Headroom, on the full-matrix stress pass (`Tests/ModulationStressTests.cpp`): the delay at its default 376 ms with feedback and mix at full travel presents **1.930 (+5.71 dBFS)** to the clipper, −0.32 dB against no effects, under the +8 dBFS ceiling; at 10 ms the same knobs are a comb with a gain of 10 at its peaks — a resonator, not a delay — and present **3.446 (+10.75 dBFS)**, which like the chorus at full feedback is held under the +14 dBFS point where the clipper stops being a net, and asserted there.

**The worst case, and the two ceilings.** Past roughly **+14 dBFS** at its input the clipper stops behaving like a net and becomes a distortion stage in its own right; the instrument gives itself **+8 dBFS** as the ceiling for the chain *at factory settings*, which leaves six decibels on the real limit. The configuration that ceiling is written against — full matrix, `res` modulated to the top, sixteen notes, unison 8 — now measures **+7.6 dBFS** with the effects off and **+7.3 dBFS** with them at factory settings, and `Tests/ModulationStressTests.cpp`, "il caso peggiore resta sotto il tetto di +8 dBFS", asserts both. One configuration deliberately sits outside that ceiling: the chorus at 100 % mix *and* 100 % feedback with the reverb off, which is the only place in the instrument where an effect adds instead of returning. It reaches **2.83 (+9.04 dBFS)** at unison 1 — more than the same setting gives at unison 8 (2.50), because eight detuned copies arrive decorrelated in the feedback loop and build less inside it. Holding *that* under +8 would cost three more decibels of instrument for a knob position almost nobody uses, so it is held under +14 instead, and asserted there.

**Where the levers actually are, measured.** `kSoftClipThreshold` is not a free one: raising it from 0.95 to 0.97 buys 0.18 dB of instrument level at constant chord margin and costs knee, so it stays at 0.95 (see **Output soft clipper** below, which also corrects what "shorter knee" means). The clipper's *shape* is not a lever for these targets at all — any curve with a ceiling at full scale refuses a chord whose peak is above full scale — so it stays too. The resonance compensation is a lever, but it is spent: `1/8` is already the largest exponent inside the 4 dB passband budget.

The constant used to be `0.4f` (-8 dB), which left the single note at -20.4 dBFS RMS — an instrument you had to lift by six decibels in the mixer before you could judge it. Before that it was `0.1f` (-20 dB), chosen when two other stages could each add uncontrolled gain: the filter multiplied its resonance peak stage by stage (see below), and `saturate()` had a small-signal slope of 1.5 so it added +3.5 dB even at drive zero. From -20 dB to -4 dB is sixteen decibels in one direction; this last decibel back is the price of the margin, not a reversal.


**Unison** (`SynthVoice`, `engine::unisonSpread`). Each voice holds a fixed array of eight `WavetableOscillator`s and runs the first N, where N is 1, 2, 4 or 8 from the `unison` choice. The copies are detuned symmetrically around the note — with N = 4 and `detune` at 18 cents: −18, −6, +6, +18 — and `unisonSpread(i, N)` returns that position on −1..+1. The same function drives both the detuning and the stereo placement, which is what keeps the outermost copy outermost in both senses.

Three things that are easy to get wrong and are pinned by tests:

*Starting phases are spread over `i / N` of the cycle.* Without that the N copies are identical at note-on and sum in phase: √N times louder with no beating until the detuning pulls them apart. Measured at `detune = 0`, unison 8: the fundamental is 0.079× the single-copy level with spread phases, and would be 2.83× (√8) without. The spreading only happens when N > 1 — at N = 1 the phase is left alone, because `start()` does not reset the oscillator and zeroing it would change the signal of a voice taking over a pool slot.

*The gain compensation is `1 / sqrt(N)`.* Summing N uncorrelated oscillators grows as the root, not linearly; without it, going from unison 1 to 8 would add about 9 dB. Measured: −16.40 dBFS RMS at unison 1 against −17.36 at unison 8.

*Unison needs a second filter.* The SVF is single-in single-out. With the copies spread across the stereo field the two channels carry different mixtures, and one filter would fold them back into one — the spread would not survive the filter, which is the point of having it. `filterRight_` exists for that and never sees a sample at unison 1, so there is no stale state to restart from when unison goes up.

The stereo width is fixed at ±0.6 (`kUnisonSpreadWidth`) because there is no `width` parameter and adding one would touch the UI, the presets and the generated files. At full width the outermost copies land entirely in one channel, and — more decisively — the spread adds to the voice's own `pan` before clamping to ±1, so at full width the cluster would already touch both edges with `pan` centred and **the pan knob would stop doing anything**. At 0.6 there are 0.4 of travel per side before the clamp bites. Constant-power panning makes the compensation exact regardless: over a symmetric set of positions the cos² terms sum to N·cos²(pan). Measured L/R correlation: 1.000 at unison 1, 0.847 at unison 8.

**Cost.** Release build, 128-sample blocks at 48 kHz, 16 held notes, 24 dB filter at Q 2 — budget is 2.67 ms per block:

| | µs/block | % of budget |
|---|---|---|
| unison 1 × 16 voices | 19.2 | 0.72 % |
| unison 8 × 16 voices | 77.1 | 2.89 % |

Eight times the oscillators cost four times the block, not eight: the envelope, level, master gain and soft clipper do not scale, and the filter only doubles. There is no polyphony cap.

**The drive saturator is a rational tanh, not a clamped cubic** (`engine::saturateCurve`, `Source/engine/SynthVoice.h`). It is the Pade [3/2] approximant of tanh, `x(27 + x^2) / (27 + 9x^2)`, flat at +/-1 beyond |x| = 3. The denominator has a triple root there (`x^3 - 9x^2 + 27x - 27 = (x-3)^3`), so the curve meets its ceiling with both first and second derivative zero.

The previous form was `clamp(x, +/-1.5)` followed by a cubic: C1 at the junction but with a corner in the second derivative, and a hard flat top above 1.5 that flattened 13.7% of the cycle at 4.8 dB of drive, 24.8% at 6 dB and 90.5% at the top of the range. That corner, not the absence of oversampling, was what the aliasing came from. Measured alias-to-fundamental at 48 kHz, direct evaluation, no oversampling: MIDI 84 at 6 dB of drive went from -75.4 to -151.9 dB, MIDI 84 at 4.8 dB from -85.2 to -169.7, MIDI 60 at 6 dB from -111.7 to -180.6 (where the float path, not the curve, becomes the floor). Above MIDI ~100 every curve converges around -43 dB: with the fundamental at 4 kHz only five harmonics fit under Nyquist and any saturation aliases. That is the point where oversampling would be the answer, and it is a separate decision.

Two things worth knowing. `std::tanh` is **worse**, measured with the same DFT: -141.4 dB against -151.9 at MIDI 84 / 6 dB, because the Pade form is exactly flat past 3 while tanh keeps curving; and it costs 1.14 ns against 0.75. And the cost of the change is +0.12 ns per sample, not zero: vectorised the two curves are indistinguishable, but inside `render()` the filter creates a serial dependency between consecutive samples, so the scalar figure is the real one. At 16 voices times 8 unison copies that is 0.7 ms per second of audio.

ADAA (antiderivative anti-aliasing) was evaluated and **rejected**: measured on this curve it is up to 21 dB *worse* at usable drive settings, because it models the input as piecewise linear between samples and, on a curve that is already smooth, that model error dominates the aliasing it removes. At drive 0 the old curve did not alias at all and ADAA injected -56 to -80 dB of noise that was not there. Surge reaches the same conclusion in practice: it implements ADAA and applies it only to rectifiers and piecewise-linear wavefolders, where the derivative jumps, and ships this same rational tanh without it.

**The `drive` knob itself was retuned, and it had a defect that only showed up when it was measured.** The gate is `if (driveGain_ > 1.0f)`: at exactly 0 dB the saturator is off, at 0.01 dB it was on at full strength. The curve is not the identity on the signal that reaches it — its slope at the origin is 1, but the oscillator arrives at full scale, where `saturate(1.0) = 0.778` — so the knob stepped **-0.94 dB of RMS (-1.31 dB of peak) in the space of a hundredth of a decibel**, and the first two decibels of travel were spent climbing back out of the hole. A knob that, nudged, turns the sound down. `SynthVoice::driveMix_` fixes it with a dry/wet between `x` and `f(x)` over the first 2 dB of travel (`kDriveFadeGain`, +2 dB): at 0.001 dB the output is the dry one to within a thousandth of a decibel, and the residual dip at half fade is 0.06 dB. Two decibels and not one because the step is 0.94 dB and the curve returns about half a decibel per decibel of drive down there, so it takes roughly two to meet without dipping; over 1 dB the residual dip is 0.27 dB, over 2 dB it is 0.06. At `drive` zero `driveMix_` is exactly zero and the branch does not run, so the default path is bit-for-bit what it was.

**And the map went from `Map::Linear 0..24` to `Map::MsSquared 0..24`**, the same quadratic map `att`/`dec`/`rel` use. The ceiling was not the problem — at 24 dB the saturation is a finished fact, not an addition — the distribution was: from 12 to 24 dB, *half the knob*, a single note gained 0.70 dB of RMS, while 0 to 12 gained 4.78. With the quadratic map half the knob sits at 6 dB, and the two halves of the travel are worth 3.85 and 5.06 dB. The ceiling is kept rather than shortened to 0..18 because `drive` is a mod matrix target: shortening it would also have changed what a route at full depth means, which is a different decision. The five presets that use `drive` were recomputed (`x → sqrt(x)`) so that each one produces the same number of decibels it produced before, to the second decimal.

**Filter resonance** (`dsp::StateVariableFilter`). Two deliberate choices keep resonance from becoming a gain stage. First, in the 24 dB configuration the resonance sits on the *last* stage only and the first stays Butterworth: applying it to both made the peak grow as Q², over +40 dB at Q 12. Second, the filter input is attenuated by `(Qbutter / Q)^(1/8)` (`kResonanceCompensation`).

The exponent is a budget, not a taste. A lowpass passband does not depend on Q, so *any* input attenuation simply lowers it: the cost is exactly `20·p·log10(Q/Qbutter)`, i.e. `30.6·p` dB at the top of the travel (Q 24), and it buys exactly the same number of decibels off the resonant peak. The budget is 4 dB of passband, and `1/8` is the largest exponent inside it: measured worst case −3.51 dB at Q 24 across 44.1/48/96 kHz and cutoffs from 100 Hz to 12 kHz, against −4.78 dB at `1/6`, which busts it. At Q 4 it costs −1.57 dB, at Q 12 −2.76 dB.

It used to be `1/32` (−0.64 dB at Q 24), and before that `1/2`, which was simply wrong: **−14.7 dB of passband at Q 24**, so turning resonance up made the whole instrument quieter and thinner instead of making the filter ring — measured on the engine at −9.99 dB of output RMS at Q 24, against +4.37 dB after that change. Going from `1/32` to `1/8` is the opposite move, made on purpose and with the eyes open: it costs 2.9 dB of passband at Q 24 and takes the same 2.9 dB off the resonant peak, which drops from +29.7 dB to **+26.8 dB** over Butterworth (2.2 dB of it at Q 12, the top of `res`'s own travel). It is the only lever in the instrument that touches the extremes harder than it touches ordinary playing, and it is spent: `1/8` is the top of the passband budget, so the joint retune above had to find its decibels in `kVoiceHeadroomGain` instead.

That peak is still the instrument's loudest source of transient level: the output soft clipper below is what keeps it in bounds. Since `res` became a modulation target this is no longer a corner case reachable only by turning a knob — a route can drive it there every LFO cycle, and the full-matrix stress test (see **Modulation**) measures **+6.0 dBFS** arriving at the clipper because of it, +7.6 with unison 8.

`res` maps to Q exponentially, 0.707 to 12 (`params::resonanceQFromRaw`), not linearly to 20: with the old linear map, `res` at its 30% default already meant Q 6.5.

**Output soft clipper** (`SynthEngine::process`). After the master gain, both channels pass through a soft clipper that is bit-transparent below `kSoftClipThreshold = 0.95f` and asymptotes to 1.0 above it. It exists because the per-voice gain is a constant: a dense chord, a high master volume or a route on `res` can still exceed full scale, and without it the host would receive hard-truncated samples. Its derivative is 1 at the threshold, so there is no corner where it engages, and it never fires during ordinary playing (see the gain-staging test above). `Tests/EngineParamsTests.cpp`, "il soft clipper d'uscita non tocca il segnale sotto soglia", pins the transparency: doubling the master gain must double the peak exactly.

The threshold was 0.8 and moved up to 0.95 with an earlier headroom rise, for the opposite reason to the obvious one: not because less signal arrives but because more does, and at 0.8 an ordinary four-note chord would have engaged it, turning the net into a permanent distortion stage. At 0.95 the chord passes untouched with **1.5 dB** to spare, and so do all twelve factory presets — the hottest of them is now *Init*, the default patch itself, at 0.828 on four notes, with 1.20 dB of margin.

**It stayed at 0.95 through the joint retune, and that was a measured decision rather than an omission.** Raising it is a real lever — the chord margin is `threshold / chord peak`, so a higher threshold allows a higher per-voice gain at constant margin — but a small one: 0.95 → 0.97 buys **0.18 dB** of instrument level, 0.95 → 0.98 buys 0.27 dB. What it costs is the knee, and the usual way of describing that cost turns out to be wrong. **The slope at an input of 1.0 is 0.25 whatever the threshold is**: the curve is `T + (1-T)·u/(1+u)` with `u = (x-T)/(1-T)`, so at `x = 1` we always have `u = 1` and a slope of `1/(1+u)² = 0.25`. What a higher threshold actually does is squeeze everything above it into a narrower output range — at an input of 1.05, `T = 0.95` maps the excess into 0.033 of output and `T = 0.97` into 0.012 — so it flattens harder while touching fewer samples. A fifth of a decibel is not worth that, so the threshold stays.

**The shape is not a lever for these targets at all.** No curve whose ceiling is full scale can pass a chord whose peak is above full scale, so the shape cannot resolve the level-versus-chord conflict; it can only change how the extremes sound. One defect in it is worth recording for whoever does take that decision: the junction is C1 but **not C2**. Below the threshold the second derivative is 0, above it starts at `-2/(1-T)`, which is -40 at 0.95 — the same class of corner that `saturate()` was rewritten to remove (see the drive saturator above). `T + (1-T)·tanh(u)` has the same slope at the junction, a second derivative of 0 on both sides, and a slope of 0.42 rather than 0.25 at an input of 1.0. It would cost a `tanh` per sample above the threshold, where the current form costs a compare and a divide, and it would change how every clipped peak in the instrument sounds — a decision that needs ears, not a recalculation.

When the clipper does fire, the numbers it fires on are: 16 held notes present 2.00, the full matrix 2.00, the full matrix with unison 8 2.39, and the worst reachable knob position 2.83. Everything between 0.8 and 0.95 stays bit-identical, which is the other half of what the threshold buys.

With the mod matrix in the picture it is no longer only a safety net for dense chords. A route on `res` or `drive` reaches the same places a hand on the knob would, but repeatedly and without anyone watching the meter, so the clipper is now a stage the instrument leans on in normal use of the matrix — it is the single reason a full matrix stays inside full scale at all. If the per-voice headroom or the resonance compensation is ever retuned, the full-matrix stress test is the measurement that says whether this stage still has anything left to give.

**A silent sustain ends the note** (`dsp::ADSREnvelope::enterSustain`). Entering the sustain stage is funnelled through one method, which drops straight to `Stage::idle` when the effective level `peak × sustain` falls below `kSilence` (−80 dB). Without it `Stage::sustain` had no path to `idle` — only release did — so a patch with `sustain = 0` left every voice occupied rendering silence until `VoiceManager` stole it with `kill()`, which is a step to zero between two adjacent samples: the click heard on percussive patches. The comparison is on the *effective* level, so a small but legitimate sustain (0.01, −40 dB) keeps holding until note-off, while a low velocity that drives the product below the threshold ends the note. It is re-evaluated every sample, so turning the `sus` knob to zero on a held note frees the voice instead of leaving it hanging.

**Retriggering a sounding note** (`VoiceManager::noteOn` → `SynthVoice::retrigger`). A second note-on for a pitch that is already sounding restarts the envelope on the same voice and touches nothing else: the oscillator phase and the two SVF integrators keep running. `noteOn` used to `kill()` the existing voice and start it from scratch, which zeroed all three at once — a step from full amplitude to zero between two adjacent samples, measured at 0.24 at full scale. That was the click heard on every repeated note, including ordinary legato. Pinned by `Tests/VoiceStealingTests.cpp`, "ribattere una nota che suona gia' non produce un gradino".

**Voice stealing takes the quietest releasing voice, and fades it.** `VoiceManager::chooseVictim` prefers the voice with the lowest amplitude among those in release, breaking ties by age — not a textbook case, since with `sustain = 0` a released chord has every voice at exactly zero and without the tie-break the pool order would decide. With nothing in release it takes the oldest still held. The previous round-robin could steal a voice that had just attacked in preference to one already fading out.

The stolen voice is not reused. `maxVoices` now means *voices that can sound together*, not pool slots: alongside it sit `stealFadeMargin = 3` and `poolSize = 19`, and stealing triggers on the active count rather than on a full pool. The victim gets an 8 ms exponential fade to −80 dB — the same shape and silence floor as the envelope's own release — while the new note takes a genuinely free slot. Surge's margin is 3 and Vital's is 1, but Vital's pool is 32: the relative margin is what matters, and 3/16 is nearly double 1/32. What the margin buys is how many steals fit inside one fade window; at 1, two notes 8 ms apart exhaust it, which is two sixteenths at 250 BPM or a chord played slightly spread.

The fade is bit-transparent by construction rather than by numerical coincidence: at rest the gain and its coefficient are exactly `1.0f`, so the multiply is an IEEE identity and the envelope value passes through untouched. There is no branch in the per-sample loop.

Measured with sixteen held notes and eight steals, the largest jump between adjacent samples went from 3.60× the waveform's own slope to 1.20×. Two details of that measurement are load-bearing and not decoration: it runs on the sine end of the table, because at frame 0 the sawtooth's legitimate slope *is* the voice amplitude (peak 0.430 against a 0.427 step, a ratio of 1.005) and no measurement there can tell a step from the waveform; and the held notes sit in MIDI 55..70, because the fade's first sample drops 2.4% of amplitude while a sine moves by 2πf/fs, and the two are equal at 183 Hz — below D2 the fade would be steeper than the wave it is fading and the test would be measuring its own choice of register.

One case still steps: `reclaimQuietestFading()`, reached only when more than three steals land inside one 8 ms window, reuses the fading tail that is furthest along. It is the declared degradation, and it is the same choice Surge makes — the only voices it truly deallocates are the ones already in uber-release.

**Envelope timing.** `dsp::ADSREnvelope` (`Source/dsp/ADSREnvelope.cpp`) derives each stage's per-sample coefficient from an exact time constant, not a rounded approximation: attack reaches 0.99 of the peak in the nominal `att` seconds, decay covers 99% of its distance in `dec`, release falls under -80 dBFS — and the voice is freed — in `rel`. The constants are `ln(100)` for attack and decay and `ln(10000)` for release. Decay's 1% tolerance is checked against `decayDistance_`, the distance from peak to the sustain target *at the start of the decay stage*, not against the peak itself: an earlier version compared against the peak, and with sustain near 1.0 the peak-relative tolerance was wider than the actual (tiny) distance left to travel, so the stage's exit condition was already satisfied on the first sample and the decay curve never ran.

## Modulation

**From the `MODS` node to the snapshot.** An assignment is made in the web UI by dragging a source onto a knob. It travels `setMods` → `bridge::StateChannel` → `state::setMods`, which rewrites the `MODS` child of the APVTS `ValueTree` as one `MOD` node per assignment, each carrying `src`, `target` and `depth`. Nothing on the audio thread ever reads that tree. `PluginProcessor` listens on the APVTS root, filters for `MOD`/`MODS` nodes — every knob movement in the plugin also passes through that listener, and rebuilding on each of them would be pure waste — and calls `state::buildModSnapshot` (`Source/state/StateToEngine.cpp`: the engine does not include the saved format), which translates the tree into a fixed-size `engine::ModSnapshot`: 32 routes in a plain array, no pointers, no allocation.

That translation happens on the message thread on purpose. It is where the string `"cutoff"` becomes index 0 in `kModTargets`, where a source name the engine doesn't know is dropped, and where `depth` is clamped to ±1 — a hand-edited preset or a newer UI could send anything, and the audio thread should not have to distrust its own input. What reaches `SynthVoice` is an array index into `modBase` and a float: no string comparison, no lookup, no validation, nothing that could fail. **The audio thread never sees a route it cannot apply.**

**Four ring slots, not a double buffer.** `SynthEngine::setMods` copies the snapshot into one of four slots (`modRing_`) and publishes only the pointer; `process()` loads it once per block. Two slots would be the obvious choice, and it is the wrong one here: mod assignments change far more often than a wavetable does — dragging a depth slider produces a stream of publishes — and with two slots the writer can come back around and overwrite the very slot the reader is holding. With four, the message thread would have to publish four times inside a single audio block to catch up with the reader, which does not happen in practice; and even then the damage would be one block of wrong modulation, never a read of freed memory, because the slots live as long as the engine. The write index is a `fetch_add`, not a plain increment, so two concurrent publishers pick different slots instead of interleaving into one.

**Rebuilds are coalesced, but `replaceState` is not.** `state::setMods` rewrites the whole list as `removeAllChildren` + N appends, so a single depth drag produces 2N notifications — and one of the intermediate states is *the empty list*, right after `removeAllChildren`. Publishing a snapshot per notification would publish that state too: if an audio block lands in that window the modulation disappears for 128 samples, which on `level` or `pan` is a click. So the listener only calls `triggerAsyncUpdate()` and `handleAsyncUpdate` rebuilds once per message-loop turn, seeing only the final state. (`bridge::StateChannel` coalesces its `emitState` for the same reason.)

`setStateInformation` is the deliberate exception. Loading a project or a preset replaces the tree wholesale while the audio thread is still rendering with the *previous* patch's assignments; waiting for the next message-loop turn would mean playing the new sound through the old modulation. So that path cancels any pending update and rebuilds synchronously, in a fixed order: recreate missing children (a project saved before `MODS` existed has none), re-attach the listener to the new tree — staying on the old one would mean never seeing a mod change again — then rebuild.

**Four sources, and their scope is the point.** `env` and `vel` are **per voice**: two held notes sit at different points of their own envelopes, and the velocity that opened each of them is its own. `mw` (CC 1) is **global** — one wheel, all voices. `lfo` is whichever of the two the patch asks for: with `lfoRetrig` on, each voice runs its own `dsp::Lfo`, restarted from `lphase` at note-on, which is what makes a vibrato repeatable; with it off, all voices read the engine's free-running LFO, advanced once per block in `process()` whether or not anything is sounding. That free LFO costs nothing when unused — voices only read its level if a route points somewhere — so it runs unconditionally rather than being switched on and off. `SynthEngine::getLfoLevel` follows the same fork when it feeds the editor's LFO dot: the first sounding voice's LFO when `lfoRetrig` is on (zero when nothing is playing), the free one when it is off (`MeterFrame::lfo`, overwritten rather than peak-held, because a bipolar LFO has no meaningful block peak). When `lsync` is on its rate comes from the host tempo via `dsp::syncedRateHz`; without a playhead, or with a host that exposes no BPM, it falls back to 120, the same fallback `syncedRateHz` applies internally, so there is no special case to keep alive. The four levels are not all the same shape: `lfo` is bipolar −1..1, the other three are 0..1.

**Eight targets; the rest are dropped on the message thread.** `engine::kModTargets` lists `cutoff`, `res`, `wtpos`, `level`, `pan`, `fine`, `drive`, `warp` — the parameters the engine can currently move per block. The UI, by contrast, lets a source be dropped on *any* knob (`ModAssignment.target` is a `ParamId`), and the list of what the engine can modulate is one line in `parameters.json` (`"modTarget": true`): `gen-params` emits `params::kModTargets`/`kModTargetIds` for the engine and `MOD_TARGETS` for the UI from it, so a knob outside the list refuses the drop (`ParamKnob` passes no `onDropMod`), and an assignment that reaches the tree anyway (an old preset, a hand-written one) is discarded by `state::buildModSnapshot` and shown as *non modulabile* in the Mod tab, where it can be removed. The order of the eight is the JSON order and nothing saved depends on it.

**The sum happens on the normalised value, and the clamp is part of the contract.** `EngineParams::modBase` carries the raw 0..1 value of each of the eight targets alongside the already-denormalised fields. `SynthVoice::modulated` computes `clamp01(base + Σ depth × sourceLevel)` and only then converts to Hz, to Q, to a gain. The order matters because it is exactly what `liveValue()` in `WebUI/src/synth/mod.ts` does, so the knob's modulation ring on screen and the sound describe the same number. The clamp is not a precaution against overflow: `liveValue` clamps at the same place, and without it the screen and the ears would disagree at the ends of the travel — the knob pinned at maximum while the filter kept climbing.

The conversion itself is shared, not re-derived: `params::cutoffHzFromRaw` and its six siblings were carved out of `collectEngineParams` precisely so the modulated path could call the same function the unmodulated one does. Two copies of the same formula diverge at the first edit, and the symptom would be a cutoff landing somewhere else depending on whether an LFO or a hand moved it. `Tests/ParamCollectTests.cpp`, "le conversioni estratte coincidono con quelle di collectEngineParams", is the guard.

**The `kModTargetIds` trap, and why it is now a compile error.** There are two parallel tables: `kModTargets` (a `ParamSlot` per target) and `kModTargetIds` (the string the UI sends). Deriving the id by indexing `params::kTable` with the slot resolves every target to the wrong parameter, because `ParamSlot`'s order is generated from `parameters.json`'s declaration order and `kTable`'s order is the file's own — `kTable[(int) ParamSlot::cutoff]` is in fact `"level"`. Now that the slot table is generated, `specForSlot()` provides the correct bridge, and two `static_assert`s close the hole: one checks that `kModTargetIds[i]` really is the id of the parameter in `kModTargets[i]`, the other that every target is a `Kind::Float`. Adding `ParamSlot::oct` to that list used to compile and reproduce the four-octave bug, since `modBase` and `modulated()` assume a normalised 0..1 value; it now fails the build with a message saying so.

**Modulation is evaluated in `render()`, not in `setParams()`.** `setParams` runs once per block, when the processor deposits the parameters; at that moment the voice may not yet have the note it is about to play, so its velocity is unknown, and `env` will have moved by the time the first sample comes out. Both are per-voice sources that change *inside* the block — a note-on can arrive halfway through the buffer, and `process()` splits the render at every MIDI event for exactly that reason. So `setParams` only caches the struct and precomputes the target mask, and `applyModulation()` runs where the voice is about to sound: at the top of each render slice, and once in `start()` before the smoothed values are snapped, so a new note begins on its own modulated values rather than inheriting the previous occupant's.

**Only targets with a route take the modulated path.** `modMask_` holds one bit per target, rebuilt once per block from the snapshot. A target with no route keeps using the already-denormalised field from `EngineParams` — which is, line for line, the code that existed before the mod matrix. That makes non-regression a *structural* property rather than a numerical coincidence between two formulas that happen to agree: with an empty matrix the output is bit-identical to the pre-modulation engine, and `Tests/ModulationStressTests.cpp` pins it sample by sample. The side benefit is that an empty matrix costs seven conversions less per block per voice, two of them `std::pow`.

**It is a control-rate system, and that is a stated limit.** Everything above is evaluated once per block, or once per slice between two MIDI events — 375 Hz at 48 kHz with 128-sample buffers, ample for an LFO that tops out at 20 Hz, and no coarser than `cutoff` and `wtpos` already were (both cost a `tan()` or a frame-index recomputation and have never updated per sample). The price is explicit: **FM and AM are not expressible in this matrix, and they are not a goal.** A per-sample modulation path would be a different design, not a tuning of this one.

**What it survives.** `Tests/ModulationStressTests.cpp`, "mod matrix a pieno carico", fills the snapshot to its 32-route ceiling — all 28 source × target combinations plus four duplicates, depths alternating ±1 so each target is pulled by two positive and two negative routes at once — and then moves the parameters underneath: `cutoff`, `wtpos`, `level`, `pan` and `fine` on coprime triangle ramps, `res` and `drive` as hard steps between the ends of their travel every few blocks, all five LFO shapes, the master gain alternating per block, mod wheel jumps mid-buffer and notes retriggering halfway through a block. It runs that at 44.1/48/96 kHz, across the three filter types and both slopes, with the LFO synced and free, with 16 voices and with 24 (which forces stealing), republishing the snapshot on every block, plus five fixed-seed fuzz passes that randomise the matrix, every parameter and the block length. The contract checked is per sample, not per peak: every sample finite, every sample within full scale, and no voice left hanging after an all-notes-off.

It holds. The worst case measures **2.00, or +6.0 dBFS, arriving at the soft clipper** (2.39 with unison 8), against an output peak of 0.9977: with `res` modulated to the top of its travel that is the filter's resonant peak — the +26.8 dB over Butterworth described above — landing on a sixteen-note chord, and the clipper is taking 6 dB off it.

**The assertion that keeps this test honest was rewritten, and the old one was the interesting part.** It used to read `peak > 0.95` on the *output*, meaning "the clipper engaged at all" — sound while the output peak sat near the threshold. It no longer does: at an input of 2.0 the clipper returns 0.9977, and four ten-thousandths of output separate "the clipper is working" from "the clipper is a wall". That assertion would have passed identically with an input of 1.0 (half a decibel of reduction) and with an input of 10 (twenty decibels), so it had stopped distinguishing the two things it was written to distinguish. The test now runs the same pass twice, once at full gain to check the per-sample output contract and once at reduced gain to measure the input, and asserts a **two-sided band on the input**: above 1.4, or the pass is not exercising the clipper (less than 3 dB of reduction) and proves nothing; below 2.512 (+8 dBFS), or the gain staging has given way. Measured 2.00, which is 3.2 dB of reduction.

**The remaining headroom is 6 dB at factory settings, and the ceiling is asserted rather than watched.** `Tests/ModulationStressTests.cpp`, "il caso peggiore resta sotto il tetto di +8 dBFS", pins the full-matrix / `res`-to-the-top / unison 8 case at +7.6 dBFS with the effects off and +7.3 with them at factory settings, against a +8 dBFS ceiling and a +14 dBFS point where the clipper stops behaving like a net. One knob position is allowed past +8 and asserted at +14 instead — the chorus at 100 % mix and feedback with the reverb off, 2.83 or +9.04 dBFS — because holding it under +8 would cost three decibels of instrument for a setting almost nobody uses. Anything that raises per-voice level again, or that adds a gain stage after the filter, has to come with a matching reduction in `kVoiceHeadroomGain`; the resonance compensation is out of slack and the clipper threshold is worth a fifth of a decibel.

## Arpeggiator

**It rewrites the `MidiBuffer`; it does not talk to the voices.** `engine::Arpeggiator::process` runs at the top of `SynthEngine::process`, before the event loop: it swallows the incoming note on/offs, passes everything else through untouched at its original sample position, and writes its own notes in their place. `VoiceManager`, `SynthVoice` and the whole poly/mono/legato/glide path are unchanged and unaware. It is the pattern of JUCE's ISC-licensed `ArpeggiatorPluginDemo`, minus its `juce::SortedSet`, which allocates on the audio thread.

Two things fall out of that choice for free. Sample-exactness is already there — `process()` splits the render at every MIDI event, so an arp note placed at sample 4711 is rendered at sample 4711 without anything new being built for it. And non-regression is structural rather than numerical: with `arpOn` false the first line of `process()` returns before touching the buffer, so the output is bit for bit what it was before the module existed. `Tests/ArpeggiatorTests.cpp` pins both ends of that — the buffer compared byte for byte, and an engine render whose checksum does not move when every other arp knob is driven to a different value with the switch off.

**The pattern lives in the `ARP` node and travels as a snapshot.** The sixteen steps are stored in the `ValueTree` as a **CSV string**, which is a fine thing for the message thread and an impossible one for the audio thread: tokenising it would allocate. So `state::buildArpSnapshot` turns it into a fixed-size `ArpSnapshot` (sixteen floats, clamped to 0..1) on the message thread, and `SynthEngine::setArpSteps` publishes it through the same four-slot ring and atomic pointer as `setMods`, for the same reasons written out under **Modulation** above. The listener that already filtered for `MOD`/`MODS` now also catches `ARP`, coalesces through the same `triggerAsyncUpdate()`, and `setStateInformation` rebuilds it synchronously — loading a preset while the audio thread is still running the previous pattern is the same problem as loading one with the previous modulation, and the symptom is louder.

A step's value is its **velocity**: 0 is off, anything above it is the level the note is emitted with. That is what the Arp tab already draws (click toggles 0 / 0.8, the wheel moves by ±0.1, the bar height is proportional), and it is a choice of ours — Odin separates on/off from two generic modulators, Helm and Surge have bipolar modulation steps. A null snapshot means *every step at full level*, not *no steps*, mirroring `EngineParams::mods`, where null means "no modulation" rather than "everything at zero".

**One counter, two moduli — the double index, stolen from Odin 2.** `n % 16` picks the grid step (whether the step sounds, and how loud); `n % (keys × octaves)` picks the note. The counter advances on **every** step, including silent ones, and that is what produces the polyrhythm: three held keys over a grid whose content repeats every four steps come back into phase after twelve, not three and not four. `MeterFrame::arpStep` is the grid index, published once per block like the other instantaneous meters.

**Swing keeps the pair invariant.** `T_even = T0 (1 + s/2)`, `T_odd = T0 (1 − s/2)`, chosen on the parity of `n`, so a pair always lasts `2 T0` and swing moves the second eighth without changing the tempo. Surge uses a flip-flop, which loses its place as soon as anything desynchronises it. The gate is a fraction of the duration of the step it falls in, not of an average one, so at 50 % the long and the short step each give half of themselves.

**Two time regimes, and the host decides which.** With the transport stopped the arp free-runs on its own fractional sample counter, restarted when the first key goes down after silence — the first note should sound under the finger, not at the next boundary of a grid nobody can see. With the transport running the boundaries come from the host's PPQ and are **re-anchored on every block**: a cursor jump, a loop or a tempo change re-attach the arp to the timeline instead of letting it drift for the rest of the session. A dedup on the last fired step is what stops that re-anchoring from re-emitting the same step ninety-three times inside one 12000-sample step. `arpRate` is tempo-synced in both regimes; without a playhead the BPM falls back to 120, as everywhere else.

`arpRate`'s four divisions — 1/32, 1/16, 1/8, 1/4 — live in `engine::arpBeatsPerStep`, **not** in `dsp::syncedRateHz`, which belongs to the LFO and has six different ones. Two tables that look like the same thing and are not is exactly how a knob comes to read "1/8" and play a quarter; a test converts the label `params::formatValue` produces back into beats and compares it with the table, so the two cannot drift.

**Hanging notes are prevented by structure, not by care.** The list of *sounding* notes — the MIDI number actually emitted, which with octaves is not the one pressed, plus a per-note gate timer — is completely decoupled from the list of held keys. Changing chord halfway through a pattern therefore cannot orphan anything: the old note still owns its note-off. Where a step repeats a pitch that is still sounding, the note-off is written **before** the note-on at the same sample (`juce::MidiBuffer` preserves insertion order at equal timestamps); the reverse order is a real bug in Odin, where at 100 % gate the new note-on silences the voice it just started. An `allNotesOff`/`allSoundOff` passes through to the voices and closes the arpeggio on the way. Turning the switch off while notes are held writes their note-offs into the host buffer before going quiet for good.

**Allocation.** The held keys (16), the sounding notes (16) and the output `MidiBuffer` are all sized in `prepare()`; the keys are kept ordered by insertion sort rather than `std::sort`, `Random` draws from an xorshift32 seeded once rather than building a `std::random_device` in the callback (both are Odin's), and the block ends with `midi.swapWith(output_)` — two pointers, no copy. The one honest caveat: after that swap the arp holds the host's buffer, and if it is smaller than the 2 KB reserve the next `ensureSize()` grows it once. Hosts reuse the same `MidiBuffer` across blocks, so this settles within two blocks and never returns.

**What is not there.** No latch/hold, no note-length-independent "as played" order (the list is always sorted by pitch), no separate pattern length — the grid is sixteen steps and the only way to shorten it is to leave steps off, which is what makes the double index interesting rather than a limitation. Keys held *before* the switch is turned on are not picked up: the arp only sees note-ons that arrive while it is running.

## Wavetables

Eleven tables ship under `Resources/wavetables/*.xwt`, in the order of the `wtIndex` choice options in `Source/parameters/parameters.json`, built by two different pipelines — see "Da dove vengono le tavole, e come se ne aggiunge una" below for the split and for adding one. The first six — `basic`, `saws`, `grit`, `vocal`, `bells`, `pwm` — are sourced from **Adventure Kid Waveforms (AKWF)**, CC0-1.0, provenance tracked in `Resources/wavetables/CREDITS.md`. Regenerate those six with:

    node scripts/fetch-wavetables.mjs

This re-downloads the AKWF families from GitHub and overwrites the `.xwt` files and `CREDITS.md`. It runs rarely — the `.xwt` files are committed, and this only refreshes them from source. `scripts/realign-wavetables.mjs` runs the same treatment on the committed files without touching the network.

**The pipeline is what makes Position a morph instead of a slideshow.** AKWF ships single-cycle waves that are individually peak-normalised and mutually unrelated in phase, so taking 64 of them and crossfading between neighbours produced comb filtering, not intermediate timbres. Measured on the six AKWF tables before the pipeline: adjacent-frame correlation as low as 0.299, and up to −4.6 dB of RMS lost halfway through a crossfade. The steps, in order, all in `scripts/wavetable-dsp.mjs`:

1. **Resample** each cycle to 2048 samples through its Fourier series — exact for a periodic signal, where linear interpolation would invent harmonics.
2. **Phase-align** each frame to its predecessor by the circular shift that maximises cross-correlation (computed by FFT). A circular shift of a single cycle is a pure phase offset: the amplitude spectrum is untouched, so this step costs nothing in timbre. Asserted in `scripts/wavetable-dsp.test.mjs`.
3. **Per-harmonic phase continuity** where step 2 is not enough: each harmonic's phase is unwrapped across the frames and rewritten as a least-squares line, amplitudes untouched. This one *does* alter individual frames, so it only runs where the mid-morph loss would otherwise exceed 1 dB.
4. **Anchor interpolation** where the family has 64 or more waves. The original `selectIndices` picked exactly `FRAMES` waves, which made the interpolation factor in `selectFrames` always zero — the crossfade never happened, and the 64 frames were 64 unrelated waves in a row. Now a smaller set of anchors is interpolated up to 64 frames, trading distinct waveforms for a continuous morph.
5. **Partial RMS equalisation**, gain `(rms_median / rms_k)^0.7` per frame. Not 1.0 on purpose: a narrowing pulse in a PWM sweep *should* get quieter, and flattening completely would erase differences in intensity that are musically correct. A constant gain per frame leaves the harmonic ratios alone, so it is timbrally neutral.
6. **One global scale** so the loudest sample in the whole table is 1.0 — never per frame, which is what produced the loudness pumping in the first place. This mirrors Vital's `Wavetable::postProcess`.

Measured end to end on the engine, RMS across a 32-step Position sweep: `pwm` went from 16.73 dB of swing to 4.19 dB, `grit` from 14.97 to 5.29; worst mid-morph loss across all six tables is now −0.81 dB. Adjacent-frame correlation, averaged per table, is now no lower than 0.923 (`vocal`'s mean) — the true minimum over any single adjacent-frame pair across the six tables is 0.659 (`grit`).

Steps 2–4 change which decisions depend on which: because equalisation brings neighbouring frames to similar levels, it *unmasks* cancellation that a loud frame next to a quiet one used to hide. The script therefore evaluates steps 3 and 4 against the finished table, not the intermediate one. Step 5 is not idempotent — running the script on its own output compresses twice.

**Format** (`dsp::parseXwt`, `Source/dsp/WavetableBlob.h/.cpp`): a 12-byte header — magic `"XWT1"`, little-endian `uint32` frame count, little-endian `uint32` frame size (must be a power of two) — followed by `frames × frameSize` `float32` samples, one frame after another. `parseXwt` rejects a wrong magic, a non-power-of-two frame size, a truncated buffer, sizes above its sanity caps (256 frames, 4096 samples/frame), or a misaligned pointer.

**Mipmaps** (`dsp::MipTable` / `buildMipTable`, `Source/dsp/MipTable.h/.cpp`, `Source/dsp/WavetableStore.cpp`): each frame gets `MipTable::kMaxLevel + 1` (11) band-limited copies built with an FFT. Level *k* keeps `(frameSize >> k) / 2` harmonics, half those of level *k − 1*.

**The level is fractional, and the oscillator crossfades between two of them.** `levelForFrequency` returns `t + 1`, where `t = log2((frameSize / 2) / maxHarmonics)`: the integer part is the level to read, the fractional part is the weight towards the next one down. Picking the integer level `ceil(t)` — the highest-bandwidth level that stays under Nyquist — froze the brightness for a whole octave and then dropped it in one step. Measured as spectral centroid over the fundamental, the profile was flat within each octave with an 18% cliff at every boundary: note 54 and note 56 had the same absolute centroid, 601 Hz, so going up a whole tone made the sound duller instead of brighter. With the crossfade the largest step between adjacent semitones is 2.59% and the profile decreases monotonically across all 97 notes.

It costs brightness, deliberately: the effective harmonic count is `maxHarmonics / 2` rather than `maxHarmonics`, about 6% duller on the low notes (centroid over fundamental 4.04 → 3.79 at note 24). The alternative — weighting towards the *brighter* neighbour — would read a level whose harmonics are above Nyquist, which is the aliasing the pyramid exists to prevent. Aliasing was unchanged where it was worst (−72.7 dB) and up to 4 dB better from note 48 upwards — that floor has since moved to −107 dB, because it was never the pyramid making the number but the linear interpolation below. `getSample` therefore does four table reads per sample, two frames × two levels, and `log2` runs only in `levelForFrequency`, never per sample.

**The pyramid has to reach a single harmonic.** `kMaxLevel` is 10 because that is the first level that keeps exactly one harmonic on a 2048-sample frame — a plain sine. It is needed: at 12.5 kHz (MIDI 127) only the fundamental fits under Nyquist. The earlier value, 6, stopped the pyramid at 16 harmonics, so `levelForFrequency` had nothing narrower to pick for any note above ~1.4 kHz and every harmonic above Nyquist folded back. Measured against the harmonic energy of the note: −25 dB at MIDI 90, −17 dB at MIDI 96, −6 dB at MIDI 120 — more fold-back than note. With 11 levels the same measurement sits at −88 dB across the whole keyboard (`MipTable / nessun alias udibile su tutta l'estensione della tastiera`). The band-limiting loop also had an off-by-one — `bin < harmonics` instead of `bin <= harmonics` — which was invisible while the top level kept 16 harmonics but would have made the one-harmonic level silent.

**Every level stays `frameSize` samples long.** The band limiting lives in the spectrum, not in the buffer length. An earlier version also decimated the length (`frameSize >> k` samples), which meant a note around A4 played a 64-sample table and anything higher a 32-sample one: at that length the oscillator's linear interpolation between adjacent samples adds far more distortion than the band limiting removes, and it was the single largest contributor to the instrument sounding bad. The cost is memory — `(kMaxLevel + 1) × frameSize` per frame instead of ≈ `2 × frameSize`, about 5.8 MB for a single 64 × 2048 table (11 levels × 2048 samples × 4 bytes × 64 frames = 5,767,168 bytes). Only one `MipTable` is *active* at a time, but built ones are never freed — see below, it is a deliberate policy, not an oversight — so a user who has cycled through all eleven shipped tables is holding all eleven at once: 11 × 5.8 MB ≈ 63.4 MB, not one. `buildMipTable` returns `nullptr` when a frame is shorter than 2^(`kMaxLevel` + 1) (2048) samples, because the top level would keep zero harmonics; the shipped tables are 2048 samples/frame, so this path never triggers on real material.

**Loading and lifecycle** (`dsp::WavetableStore`): tables are embedded at build time via `juce_add_binary_data(WavetableAssets ... HEADER_NAME WavetableData.h)` — the explicit header name avoids colliding with the `WebUIAssets` target, which already generates its own `BinaryData.h` for the web-bundle embed. `WavetableStore::lookupBlob` copies each embedded blob into an aligned buffer before parsing it, because JUCE's generated resource arrays give no alignment guarantee and `parseXwt` refuses a misaligned pointer. Built `MipTable`s are never freed: the audio thread reads `WavetableStore::active()` (an atomic pointer) at any time, so their memory must outlive every possible concurrent read. `PluginProcessor::prepareToPlay` and its 25 Hz timer (`kWavetablePollHz`) both call `WavetableStore::setActive` and are serialised by `PluginProcessor::wavetableLock_` (a `juce::CriticalSection`), never taken on the audio thread. The pointer itself reaches the audio thread through a single-slot atomic mailbox, `SynthEngine::setPendingWavetable`, drained once per block inside `SynthEngine::process`: handing it to the voices directly from the message thread would race with the audio thread reading the oscillator's plain (non-atomic) fields.

qualunque intervento, un limite che la sola fase non supera — non della pipeline. Sono le due
tavole meno solide della dotazione. I due `.xwt` non sono più bit-identici all'estrazione
originale da Serum (cambia la fase, non lo spettro di ampiezza); dettagli e numeri completi in
`Resources/wavetables/CREDITS.md`.

Aggiungere una tavola vuol dire quattro cose, e la quarta è la sola che si dimentica:

1. scrivere il `.xwt` in `Resources/wavetables`;
2. aggiungere l'opzione in coda a `wtIndex` in `Source/parameters/parameters.json`, col
   `value` uguale al nome del file senza estensione;
3. aggiungere la voce in coda a `kWavetableFiles` in `Source/dsp/WavetableStore.h`, nella
   stessa posizione — lo `static_assert` in `Source/engine/ParamCollect.h` non compila se le due
   liste divergono;
4. rigenerare le anteprime della WebUI con `node scripts/build-wavetable-previews.mjs`,
   altrimenti lo schermo continua a disegnare la tavola vecchia a quell'indice.

Nessuna tavola si carica da disco a runtime: `WavetableStore` legge solo da `WavetableAssets`.

I preset di fabbrica non contengono l'indice della tavola ma il suo nome
(`"wtIndex": "retro-racing"` in `Source/parameters/presets.json`): un choice si normalizza
`indice / (numOpzioni - 1)`, e senza il nome ogni aggiunta di tavola ripunterebbe in silenzio
tutti i preset già scritti. `scripts/gen-params.mjs` risolve il nome e fallisce la
generazione se non esiste.

## Presets

`Source/parameters/presets.json` is the single source of truth for the twelve factory presets. `scripts/gen-params.mjs` reads it, together with `parameters.json`, and emits four generated files: `Source/parameters/ParameterTable.h`, `WebUI/src/synth/params.generated.ts`, `Source/parameters/PresetTable.h`, `WebUI/src/synth/presets.generated.ts`.

`StateChannel::applyPreset` (`Source/bridge/StateChannel.cpp`) applies a preset on the message thread: for every spec in `params::kTable` it looks up a value in the preset's value list and falls back to the parameter's spec default (`spec.def`) when the preset doesn't mention it — this is what stops a preset from inheriting fragments of whatever sound was active before it was picked. Each parameter is set through `beginChangeGesture` / `setValueNotifyingHost` / `endChangeGesture`, so host automation and undo see the change like any other parameter edit.

**Every preset is tuned against the gain staging**, which is why each one spells out `level`, `drive` and `volume` explicitly instead of inheriting them: those three decide whether it clips. Two of the twelve have been trimmed for that reason. *Reese Wide* went from `level` 0.8 to 0.6 when `kVoiceHeadroomGain` rose from -8 dB to -3 dB and a four-note chord took it past full scale. *Acid Line* went from 0.9 to 0.8 in the joint retune, because it was the one preset measurably hotter than the default patch — 1.035 at the clipper's input on four notes, dry, which means it *was* engaging the clipper while this document claimed it reached 0.84 (that figure came from the analytic inversion, not from a measurement of the input). Leaving it there would have cost every other preset a decibel of level, since the per-voice constant is global and one preset was setting it.

`Tests/PresetGainStagingTests.cpp`, "nessun preset di fabbrica accende il clipper su un accordo di quattro note", now plays all twelve through the real `collectEngineParams` and measures both states — effects on, as the user finds them, and dry — requiring at least 1 dB of margin under the 0.95 threshold in both. Measured dry: *Init* 0.828 (the hottest, which is as it should be — it is the only patch nobody has trimmed), *Sub Pulse* 0.735, *Reese Wide* 0.707, *Neon Lead* 0.703, *Acid Line* 0.816, *Solid Saw* 0.646, *Wire Pluck* 0.640, *Cold Sweep* 0.656, *Bell Tower* 0.519, *Velvet Keys* 0.362, *Glass Pad* 0.234, *Dust Choir* 0.205. With the effects at factory settings every one of them is the same or lower, by up to 1.4 dB. The test also asserts that no preset is hotter than *Init*: a preset above the default patch is a preset that will set the instrument's headroom for everybody.

The same default-fallback rule is implemented twice — once here, once in `WebUI/src/juce/fake-backend.ts`'s `loadPreset` — because the web UI needs it without a JUCE host attached. Only the TypeScript side has a test (`WebUI/src/juce/fake-backend.test.ts`): `XerumTests` does not compile `Source/bridge/*`, so the two implementations can drift without either test suite noticing.
